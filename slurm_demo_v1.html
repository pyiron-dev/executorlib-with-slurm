executorlib with SLURM#

executorlib extends the Executor interface from the Python standard library’s concurrent.futures to distribute Python functions as jobs on an HPC cluster, without having to rewrite the functions themselves. This notebook walks through submitting a serial function, an MPI-parallel function, and nested executors via SLURM.

Based on the cmti and cmmg clusters hosted at the MPCDF for the MPI for Sustainable Materials.

import executorlib

executorlib wraps Python functions as SLURM jobs. SlurmClusterExecutor submits each function call as a separate sbatch job, while SlurmJobExecutor (used later for nested tasks) runs steps inside an already-running job allocation.

Submit Python Function to SLURM#

This is just like using sbatch to submit shell scripts. See the SlurmClusterExecutor documentation for the full set of options.

def get_slurm_env():
    import os
    from time import sleep
    sleep(5)
    return {
        k:v for k, v in os.environ.items() if "SLURM_" in k
    }

get_slurm_env is the function that will be sent to the cluster. It collects all SLURM_* environment variables from inside the running job, so we can verify which resources SLURM actually assigned. The sleep(5) gives the job a moment to settle before sampling the environment.

submission_template = """\
#!/bin/bash
#SBATCH --output=time.out
#SBATCH --job-name={{job_name}}
#SBATCH --chdir={{working_directory}}
#SBATCH --get-user-env=L
#SBATCH --partition={{partition}}
{%- if run_time_max %}
#SBATCH --time={{ [1, run_time_max // 60]|max }}
{%- endif %}
{%- if dependency %}
#SBATCH --dependency=afterok:{{ dependency | join(',') }}
{%- endif %}
{%- if memory_max %}
#SBATCH --mem={{memory_max}}G
{%- endif %}
#SBATCH --ntasks={{cores}}

{{command}}
"""

The submission template is a Jinja2 template for the sbatch script. The line #SBATCH --ntasks={{cores}} is the key mapping: the cores value in executorlib’s resource_dict becomes the number of SLURM tasks (i.e. processes). For a serial job cores=1 requests a single process. For an MPI job cores=N requests N processes — one per MPI rank. The --mem, --time, and --dependency lines are only emitted when those keys are present in resource_dict.

with executorlib.SlurmClusterExecutor() as exe:
    f1 = exe.submit(
        get_slurm_env,
        resource_dict={
            "submission_template": submission_template, 
            "run_time_max": 180,  # in seconds  
            # "partition": "s.cmfe",
            "partition": "s.cmmg",
            "cores": 1,
            "threads_per_core": 4,
        })
    result = f1.result()
    print(result)

Submit MPI parallel Python function to SLURM#

One of the key features of executorlib is supporting mpi4py parallel Python functions. See the MPI support section of the installation guide for the required dependencies.

def get_slurm_parallel_env():
    import os
    from mpi4py import MPI

    comm = MPI.COMM_WORLD
    size = comm.Get_size()
    rank = comm.Get_rank()

    env_dict = os.environ
    data = {
        k:v for k, v in os.environ.items() if "SLURM_" in k
    }
    data = comm.gather(data, root=0)
    return data

get_slurm_parallel_env is an MPI-parallel function. Each MPI rank calls os.environ independently, then comm.gather collects all per-rank dictionaries onto rank 0, which returns the combined list. Because this function uses mpi4py, executorlib must launch it with srun rather than a plain Python call — that is why pmi_mode="pmix" is passed to the executor.

The important part here is the pmi_mode="pmix" to use the right backend:

with executorlib.SlurmClusterExecutor(pmi_mode="pmix") as exe:
    f1 = exe.submit(
        get_slurm_parallel_env,
        resource_dict={
            "submission_template": submission_template, 
            "run_time_max": 180,  # in seconds  
            # "partition": "s.cmfe",
            "partition": "s.cmmg",
            "cores": 4,
            "threads_per_core": 4,
        })
    result = f1.result()
    print(result)

Nested Executors#

Finally, to gain the most of the flexibility executorlib offers the option to nest executors within each other. See the HPC Job Executor documentation for more details on SlurmJobExecutor and running nested workloads inside an existing allocation.

def get_nested_env():
    with executorlib.SlurmJobExecutor(max_workers=4, pmi_mode="pmix") as exe:
        future_lst = []
        for i in range(4):
            future_lst.append(exe.submit(
                get_slurm_env,
                resource_dict={"cores": 1, "threads_per_core": 1},
            ))
        return [f.result() for f in future_lst]

get_nested_env runs inside a SLURM job and itself creates a second-level executor. SlurmJobExecutor re-uses the existing allocation instead of submitting new sbatch jobs: it dispatches each of the four get_slurm_env calls as an srun step within the parent job. The outer job is allocated cores=1, threads_per_core=4 (one task slot with 4 CPUs). Each inner step requests cores=1, threads_per_core=1, so four steps share the available CPUs — this is valid because the outer allocation has enough CPU resources to run them.
